# ToolPeak

Ten free online tools that run entirely in your browser — no account, no
upload, no server. A static site generated by a small Node script and served
from Cloudflare Pages.

```
npm install     # devDependencies only; the site itself ships zero dependencies
npm run dev     # build, then serve on http://localhost:8080
npm run admin   # admin panel on http://localhost:8081 — settings and articles
npm run check   # build + the full test suite (this is the gate before deploying)
```

---

## Why the site is built this way

Every tool computes in the visitor's browser. Nothing is uploaded, so there is
no server to run, nothing to breach, and no per-visitor cost. That makes the
honest privacy claim on the front page cheap to keep: it is not a policy
decision, it is the architecture.

Each page is self-contained — inline CSS, inline JS, no external fonts, no CDN.
A cold load is a single request and a single round trip. Pages land between
17 KB and 33 KB gzipped, so the site opens in well under two seconds on a
mobile connection.

## Repository layout

```
build.js               the generator: src/ -> dist/
site.config.js         all configuration, read from environment variables
src/
  lib/                 pure logic, no DOM (tools-core, qr, diff)
  app.js               DOM wiring for all ten tools
  consent.js           cookie bar and the consent-gated ad loader
  templates.js         page shell, JSON-LD, the tool registry
  styles.css           design system
  pages/tools/         one module per tool: copy, FAQs, markup
  pages/legal.js       about, contact, privacy policy, terms
  content/blog/        one module per article
scripts/
  admin.js             local admin panel: settings and article editor
  admin-ui.html        the panel's interface
  new-post.js          scaffolds a blog post
  serve.js             static file server for local preview
tests/                 the test suite (see below)
dist/                  build output, git-ignored
```

Adding a tool means adding one file to `src/pages/tools/` and registering it in
`TOOLS` in `src/templates.js`. Adding an article means one file in
`src/content/blog/`, which `npm run new-post` will scaffold for you.

## Configuration

Nothing secret lives in this repository. `site.config.js` reads everything from
the environment, with safe defaults for local work. `.env.example` documents
every variable, and a test enforces that the file and the code never drift
apart.

For production, set these in **Cloudflare Pages → Settings → Environment
variables**:

| Variable | Purpose |
|---|---|
| `SITE_URL` | canonical URLs, sitemap, RSS. No trailing slash |
| `CONTACT_EMAIL` | shown on the Contact page and in the Privacy Policy |
| `PUBLISHER_NAME` | schema.org publisher and the copyright line |
| `ADS_POPUNDER` | Adsterra popunder snippet |
| `ADS_SOCIAL_BAR` | Adsterra Social Bar snippet |
| `ADS_BANNER` | one in-content banner snippet |
| `ADS_TXT` | the exact line from the Adsterra dashboard |
| `CF_BEACON_TOKEN` | optional Cloudflare Web Analytics |
| `GOOGLE_SITE_VERIFICATION` | optional, if not verifying by DNS |
| `BING_SITE_VERIFICATION` | optional |
| `PINTEREST_SITE_VERIFICATION` | optional; claiming the domain brands every pin |

**The ad snippets contain your Adsterra account ID.** Committed, they can be
lifted and pointed at someone else's traffic — which is both stolen revenue and
a banned account. They stay in Cloudflare. Leaving them unset simply disables
that unit, which is the correct state until the site is approved.

## Ads and consent

The rule is fewer ads and more pageviews. Per page, at most:

- **1 popunder** — fires on load, occupies no space
- **1 Social Bar** — mobile
- **1 banner** — mid-content

There is no configuration path to a fourth unit. No interstitials, no sound, no
banner stacks. Tests assert the ceiling rather than trusting discipline.

The cookie bar offers **Accept** and **Decline**, one click each. It is a
docked landmark, not a modal: it never traps focus and never locks scrolling.
Decline loads zero ad code and every tool keeps working — verified by tests
that wait out the deferred loader and then use the tools.

Ads are deferred to `requestIdleCallback`, so they can never delay a tool
becoming usable.

## Tests

```
npm test        # 317 tests, ~60 seconds
```

| Suite | Covers |
|---|---|
| `tools-core.test.js` | the pure math behind every tool |
| `qr.test.js` | QR encoder against ISO/IEC 18004 structure |
| `diff.test.js` | Myers diff, including pathological inputs |
| `tools-dom.test.js` | all ten tools driven through their built pages |
| `consent.test.js` | consent gating and the ad ceiling |
| `qr-scannable.test.js` | rendered codes decoded by an independent library |
| `build.test.js` | output: word counts, FAQs, links, metadata, page weight |
| `config.test.js` | env documentation, no committed secrets, scripts |
| `ad-integration.test.js` | Adsterra snippet shapes, layout stability, ads.txt |
| `deploy.test.js` | works on GitHub Pages and Cloudflare without rewrites |
| `admin.test.js` | the admin panel's file writing, escaping and localhost binding |
| `adsnippet.test.js` | Adsterra snippet checking, the document.write rewrite, ads.txt |

Two things are worth knowing about the suite.

**`qr-scannable.test.js` rasterizes the SVG the page actually renders and hands
the pixels to `jsQR`.** A QR matrix can satisfy every internal invariant and
still be unreadable, so structural tests alone prove less than they appear to.
This asserts on what a phone camera would get back.

**`build.test.js` enforces the editorial rules mechanically** — 300+ words and
four FAQs per tool page, no broken internal links, titles inside the 60
characters Google displays, no Bengali characters, no British spellings, no
taka symbol. These are the things that get a site rejected or quietly ignored,
and they are easy to violate months from now.

Writing the suite found three real bugs: `age()` returned negative days across
month boundaries, `age()` pushed the next birthday a year out when asked on the
birthday itself, and Wi-Fi QR codes for open networks emitted a malformed empty
password field.

Note that `node --test tests/` fails on this Node version — the directory is
resolved as a module. Use `npm test`, which passes a glob.

## Deploying to GitHub Pages (free, no domain needed)

**The repository must be named `yourname.github.io`.** Any other name serves
the site from a subdirectory, where every root-relative link 404s and
`ads.txt` becomes unreachable by ad networks.

1. Create a public repository named exactly `yourname.github.io`.
2. Push this code to `main`.
3. **Settings → Pages → Source: GitHub Actions.**
4. **Settings → Secrets and variables → Actions**, Variables tab: set
   `SITE_URL`, `CONTACT_EMAIL` and `PUBLISHER_NAME`. Ad snippets go in the
   Secrets tab.

`.github/workflows/deploy.yml` runs the test suite, builds, and publishes. It
also writes `.nojekyll` so Pages does not hide underscore-prefixed files.

`_redirects` and `_headers` are Cloudflare features and are ignored here, so
extensionless URLs will not resolve. Nothing depends on them — every link
already includes `.html`, and `deploy.test.js` enforces that.

See `ADSTERRA.md` for the trade-offs versus a paid domain.

## Deploying to Cloudflare Pages

1. Push to GitHub.
2. Cloudflare dashboard → **Workers & Pages** → **Create** → **Pages** →
   connect the repository.
3. Build command `npm run build`, output directory `dist`. No framework preset.
4. Add the environment variables from the table above.
5. **Custom domains** → add the apex domain and `www`.

`_headers` and `_redirects` are generated into `dist/`, so security headers and
extensionless URLs (`/tools/word-counter`) work with no dashboard
configuration.

### After the first deploy

- Verify the domain in **Google Search Console** and **Bing Webmaster Tools**,
  then submit `https://yourdomain.com/sitemap.xml` to both. Bing feeds
  DuckDuckGo, so it is worth the five minutes.
- Confirm `https://yourdomain.com/ads.txt` returns your real Adsterra line. It
  returns a placeholder comment until `ADS_TXT` is set, which is intentional —
  the URL should never 404.
- Claim the domain on Pinterest before pinning.

## The admin panel

```
npm run admin        # http://localhost:8081
```

A local control panel for the two jobs that otherwise mean editing files by
hand: pasting ad codes, and writing articles. Five tabs — a dashboard, ads,
the article list, a writing view, and settings — plus buttons to rebuild the
site and run the tests.

The **Ads** tab checks each snippet as it is pasted, because the three
Adsterra units look alike and a wrong paste fails silently. It reads back the
key, size and serving host so a correct paste gets confirmed; it catches
banner code in the popunder box, `http://` that a browser will block as mixed
content, and the same key used twice. Below that, a panel reads `dist/` and
reports what the built site would really serve — saved settings and live ads
are different things, and only the second one earns anything.

It also rewrites `document.write`. Adsterra still issues banner code built on
it, and because ads here wait for a consent click they always run after the
document has closed — where `document.write` implicitly calls
`document.open()` and blanks the page. The rewrite keeps the `atOptions` block
and its ordering, and swaps the written tag for a plain async one.

**It is a development tool and must never be deployed.** There is no login, it
writes files, and it can run builds. It binds to `127.0.0.1` for that reason,
and a test enforces the default. Nothing under `scripts/` is ever copied into
`dist/`, so it cannot leak into a deploy by accident.

Settings are written to `.env`, which is git-ignored. The precedence is:

```
real environment variable  >  .env  >  default in site.config.js
```

A real environment variable always wins, so a local `.env` cannot change what
Cloudflare Pages or GitHub Actions build. **`.env` only configures your own
machine.** For the live site the same values have to be set again in the host's
dashboard — the panel says so on every settings field.

## Publishing an article

Either use the **Write** tab in the admin panel, or scaffold from the terminal:

```
npm run new-post -- "How to Compress a PDF Under 1 MB" --tools image-compressor
```

This writes a correctly shaped module with today's date and four FAQ stubs.
Replace every `TODO`, then run `npm run check`.

The target is one genuinely useful article per week. What that means in
practice:

- **Answer in the first sentence.** Someone who reads nothing else should
  already have what they came for.
- **Write from something you checked.** Real numbers, a worked example, and
  the edge case everyone hits. That is what earns links.
- **Link to the tool that does the job**, via `related`.
- **US English, dollars and pounds, both metric and imperial.**

One good page beats ten generic ones. Bulk-generated filler does not rank, and
at scale it puts the ad account at risk.

### Things that will get the account banned

Clicking your own ads. Asking anyone else to. View-exchange groups, traffic
bots, paid "traffic" services. Republishing someone else's writing.

None of it survives review, and Adsterra withholds the balance when it catches
it. The traffic plan here is slow because the durable version is slow: real
pages answering real searches, indexed properly, shared where the audience
already is.
